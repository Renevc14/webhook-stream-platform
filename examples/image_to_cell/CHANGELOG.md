- **SH-178 — lifecycle zombie cleanup deleted OTHER orgs' webhooks (cross-org crossfire).** Smartsheet's `GET /webhooks` is scoped to the token's USER, not to our org. When one Smartsheet account backs multiple Smarthub orgs (staging: two orgs, one Smartsheet user), each org's health-check cycle saw the other org's webhooks, classified them as "Type 1 — wrong worksheet" zombies (their sheets are not in *this* org's configs), and deleted them — the orgs destroyed each other's webhooks every 5 minutes in an endless delete/re-register loop. If the cross-org ownership lookup fails, cleanup **fails closed** (nothing deleted that cycle, WARN logged); the create-config registration path (`configs._register_webhook_for_config`) likewise refuses to run its destructive pre-cleanup without ownership data and lets the lifecycle retry. The zombie scan also re-reads the org's DB webhooks after step 2, so a webhook adopted into the DB earlier in the same cycle is no longer flagged stale and deleted moments after being adopted. Health-check summary gains an `unowned_skipped` counter. New repo helper `WebhookRepository.get_by_worksheet_all_orgs`. 30 regression tests in `test_sh178_lifecycle_cross_org_cleanup.py`. Note: this is section A of SH-178; the runner-identity/failover work (section B) depends on the broker's explicit revoked state and ships separately.

- **SH-176 — name_map rows silently dropped images under concurrent cellimages writes.** Reported by Beth (2026-07-07, sheet `695569967173508`, config "PG Inventory - Name Map"): rows with two image columns intermittently lost one image to a spurious Smartsheet `1004` ("not authorized"), even though the org token had edit rights (dozens of successes on the same sheet, failing column alternating per row). Root cause: `ImageHandler.process_batch` uploaded a row's images concurrently (`asyncio.gather`), so two `POST .../cellimages` hit the **same row** within tens of ms; Smartsheet rejects concurrent same-row cellimages writes with a transient `1004`, which is non-retryable by design, so the losing image was dropped. Fix: (1) a per-row `asyncio.Lock` in `_process_parallel` serializes the cellimages upload step while download + conversion stay parallel; (2) defense-in-depth bounded retry (`CELLIMAGES_1004_MAX_RETRIES=2`) for a transient `1004` in `AttachmentService.upload_bytes_to_cell` — a genuinely unauthorized target still surfaces after retries (logged + raised → DLQ); (3) async port of the prod `failed_attempts` follow-up — `name_map` tracks per-attachment upload failures in `imagetocell_row_states.failed_attempts` (additive migration, default `{}`) and retries up to `NAME_MAP_MAX_UPLOAD_ATTEMPTS` (default 5) instead of looping forever or abandoning a failed column when a sibling succeeds. ### Added
- **SH-135 — Automatic billing-cycle rollover for the atomic bolt-cap.** The Redis counter `bolt-cap:{org_id}:consumed` introduced by SH-103 persists across the cycle for atomicity, but Postgres effectively resets `consumed_bolts_start` at the cycle boundary. Until this ticket, the Redis counter stayed at the previous cycle's accumulated value when a new cycle started — the customer-visible symptom was "blocked far earlier than entitled" and the workaround was a manual `DEL` documented in the function docstring. SH-135 closes the gap. A new sibling Redis key `bolt-cap:{org_id}:cycle_id` carries the last seen `subscription_status.current_cycle_start`. A new `smarthub_core.db.redis.RedisClient.atomic_deduct_with_cycle` helper extends `atomic_deduct` with a cycle-aware preamble: it compares the stored cycle id against the caller's expected value, and if they differ (or the key is missing) atomically resets `consumed_key` to `cycle_baseline` and updates `cycle_id_key` *inside the same Lua execution* before evaluating the deduct. Two requests arriving in the same millisecond as the rollover cannot race — exactly one applies the reset, the other sees the post-reset state, both deduct against the new cycle. `load_i2c_org_usage_context` now surfaces `current_cycle_start` in its returned dict, and `bolt_cap.atomic_reserve_bolts` routes through the cycle-aware helper whenever the RPC yields a cycle id (falls back to the cycle-less `atomic_deduct` otherwise, still seeded with the source-of-truth baseline). End-to-end concurrency test against a local Redis: 100 coroutines, cap of 300, mid-flight rollover from one cycle to another — exactly 20 succeed in the new cycle, consumed counter ends at 300, cycle id reflects the new cycle. No double-bill risk in either direction.

### Added
- **SH-103 (part 2) — `atomic_reserve_bolts` consumes the new helper from inside i2c-3.** New async function in `bolt_cap.py`. Each mid-job bolt-cap check (the per-row branch in `RowProcessor.process`) now:
  1. Computes the cycle ceiling from `load_i2c_org_usage_context(org)` and writes it into `bolt-cap:{org}:limit` with TTL 60s.
  2. Seeds `bolt-cap:{org}:consumed` from the Postgres consumed-bolts-start via `SET NX` so the in-Redis counter starts from the cycle baseline.
  3. Calls `RedisClient.atomic_deduct(consumed_key, limit_key, requested_bolts)`. Two workers can no longer both pass the cap check and collectively overshoot — the read+INCRBY is serialised atomically in the Lua script.
  When Redis is not wired (no client installed, or the seed / atomic_deduct calls surface anything unexpected — including the `MagicMock` instance the unit tests use to satisfy SH-93 wiring), the helper transparently falls back to the legacy per-process `get_remaining_image_capacity` peek. The TOCTOU window re-opens in degraded mode but nothing hard-fails. If `atomic_deduct` denies the full batch, the caller progressively halves the request (`n → n//2 → ...`) and retries — so a row that wants to process 4 images can still get budget for 1 or 2 instead of skipping outright. Source of truth for billing remains `imagetocell_usage_log` in Postgres; the Redis counter is a fast-path enforcement cache. Billing-cycle rollover is currently a manual reset (`DEL bolt-cap:{org}:consumed`) — documented in the function docstring; automatic detection is a follow-up.
- **SH-103 (part 1) — `RedisClient.atomic_deduct` in `smarthub_core`.** New atomic check-and-deduct helper for billing / quota counters, backed by a Lua script that reads the consumed counter + limit and conditionally `INCRBY`s the counter in a single execution. Fixes the TOCTOU gap that the current 30-second-cached bolt-cap check carries: under burst load N parallel workers all read the same `remaining=N` and collectively overshoot the cap. With `atomic_deduct` two callers cannot both observe headroom and both succeed — the Lua execution serialises the read+write atomically. Default-open when the limit key is missing (treats limit as `+∞`, returns `(True, -1)`) so a cache miss does not hard-fail billing flows. Fail-closed on `RedisError` (returns `(False, 0)`) — diametrically opposite to `rate_limit_consume` which fails open, because letting a caller proceed unmetered on a Redis hiccup is exactly the customer-visible double-bill that SH-98 / SH-108 closed at neighbouring layers. Concurrency-tested against a local Redis: 100 coroutines each requesting 1 unit against a cap of 50 succeed exactly 50 times; consumed counter ends at 50. The i2c-3 integration (SH-103 part 2 — bolt-cap migrated to the atomic primitive) follows on the same branch.

### Security
- **Smartsheet webhook shared secrets are now encrypted at rest.** `imagetocell_webhooks.shared_secret` (the value used to validate the HMAC of every incoming Smartsheet webhook event) was previously stored as plain text. Anyone with read access to the row could forge signed webhook calls and impersonate Smartsheet, with downstream impact on cell content and billing. `WebhookRepository.save()` and `update_secret()` now AES-256-GCM-encrypt the value with the same `APP_CRYPTO_KEY` used for Smartsheet PATs; every read path (`get_secret`, `get_by_worksheet`, `get_by_webhook_id`, `get_all_active`, `get_for_organization`) decrypts transparently so callers see plaintext as before. Encryption is idempotent — already-encrypted values pass through unchanged. A dual-read fallback honours legacy plaintext rows (with a WARN log) so the deploy is zero-downtime; the existing rows are re-encrypted by `scripts/migrate_encrypt_webhook_secrets.py` after the deploy.
- **Webhook lifecycle recovery no longer re-introduces plaintext secrets.** `WebhookLifecycleManager._save_webhook_to_db` bypassed `WebhookRepository.save()` and wrote the raw `webhook.shared_secret` directly to both `imagetocell_webhooks` and the secondary `worksheet_webhooks` table on every recovery / re-registration. The first iteration of the SH-108 backfill verified this in staging — a freshly recovered webhook landed in the DB as a 26-char ASCII string. The lifecycle now wraps both writes with the shared `_ensure_encrypted_secret` helper, so every recovery path produces ciphertext.

## [1.2.0] - 2026-05-28

**Category:** Backend · **Impact:** MINOR

Shipped as part of platform release **1.3.0**.

### Added
- **Name-map mode now reads the "filename contains" pattern set in the UI.** The pattern configured per column ("place into column 2 when the filename contains *horse*") is now honored as expected. Previously the backend ignored those fields and matched the attachment filename against the column display name instead, which rarely behaved the way the configuration suggested. Slots left without a pattern keep the previous column-name fallback.
- **`PriorLogUnavailable` typed exception + retry helper for the `imagetocell_usage_log` lookup.** The prior-processed query that drives backfill synthetic state now retries 3× with exponential backoff in `i2c_bolt_gate._fetch_prior_processed` and raises `PriorLogUnavailable` on exhaustion. Callers (`preflight_backfill_budget` and `ImageProcessor._build_synthetic_states_for_backfill`) catch it and abort the backfill with a clear retryable error message instead of silently treating the failure as "no prior history" — the path that produced the customer-reported double-bills.
- **`bolt_cap.invalidate_usage_cache(org_id)` helper.** Lets the backfill orchestrator drop the 30-second cap-context cache after a backfill so subsequent configs on the same worksheet see fresh consumed-bolts numbers and cannot skip past the budget gate using a stale snapshot.

### Fixed
- **Backfill restored after a Smartsheet API change broke the full-sheet read.** Smartsheet began rejecting the sheet fetch used by backfill — `GET /sheets/{id}?include=attachments` — with HTTP 400 (errorCode 1008, "Unable to parse request"), so every backfill finished with `0 processed, 0 skipped, 0 failed`. Live webhook processing was unaffected because it reads attachments per-row, where the option still works. `SheetService.get_sheet` now fetches rows without that include and merges attachment metadata from the dedicated List Attachments endpoint (grouped by `parentId`), with no change to how images are processed or billed.
- **Default mode no longer overwrites manually-placed images.** Configured cells that already hold an image — whether the user uploaded it directly or it was placed by a prior run — are skipped end-to-end. New attachments are routed only into empty cells, so existing content is never replaced.
- **Default mode re-fills cells that the user manually clears.** Clearing a cell now makes the slot available again for the next attachment that arrives. Previously, once a row had been fully processed it was treated as "complete" forever and subsequent uploads were silently ignored.
- **Default mode skips attachments whose filename already shows on a configured cell.** When the same file is uploaded again (a common case after partial retries or template-based row creation), the attachment is recognised and dropped — no duplicate upload, no double charge.
- **Webhook-driven uploads in default mode only consider the attachment that triggered the webhook.** Previously the whole row's attachment list was re-evaluated on every event, which could re-bill older files that were already processed.
- **Replace mode keeps the newest N attachments visible across the configured columns when files arrive one at a time.** The typical webhook pattern (a single new attachment per event) now correctly re-orders the columns so the freshest images sit in the first slots, rather than leaving the first column pinned to the earliest file. Re-ordering already-processed attachments between columns is not billed.
- **Concurrent attachment uploads no longer drop events.** Several files uploaded together — common when using Bulk Attachment Uploader or when a user attaches multiple files at once — are each routed to their parent row and processed in parallel, instead of one event blocking the others.
- **Backfill double-bill on transient Supabase failures (customer-reported).** Several cooperating root causes were causing every backfill on a no-change worksheet to re-bill already-processed images:
  - `_fetch_prior_processed` now paginates with `range(offset, offset+499)` so the PostgREST default 1000-row response cap can no longer silently truncate results when `imagetocell_usage_log` has many historical entries.
  - `row_ids` are chunked into batches of 500 before the `IN()` clause so URLs stay under ALB / proxy size limits even with thousands of rows (the source of the previously-reported `400 — JSON could not be generated` from this query).
  - Both fail-open `except: return {}` paths (in `i2c_bolt_gate._fetch_prior_processed` and `ImageProcessor._build_synthetic_states_for_backfill`) are replaced by retry-then-raise. `_backfill_config` catches `PriorLogUnavailable` and returns `BackfillResult(success=False, error="prior_log_unavailable: ... safe to retry")` instead of silently re-processing every row.
- **Replace-mode billing — no-change re-runs now bill 0 bolts.** `ReplaceMode.filter_attachments` was ignoring `state.last_ids` and always returning the newest N attachments, re-uploading and re-billing on every backfill regardless of whether the cell content changed. Combined with `_build_synthetic_states_for_backfill` short-circuiting for replace mode, every replace re-run on an unchanged sheet billed N bolts per row × every row. The filter now subtracts `state.last_ids` from the newest-N candidates, and the synthetic-state build includes replace mode, so a no-change re-run returns `[]` and bills 0. Genuinely new attachments still bill normally. Estimator (`preflight_backfill_budget`) and runtime now agree on the per-row image count.
- **`state_repo.save` failure no longer triggers a re-bill on the next backfill (partial fix).** `log_usage` now runs before `state_repo.save` in `RowProcessor.process`, inverting the failure-mode trade-off: if `state.save` fails after a successful upload, the usage_log entry is already written so the next backfill's synthetic state build sees the row as processed and skips it. Worst case is now subcobro (lost revenue) instead of double-bill (customer-visible overcharge). Full idempotency requires a UNIQUE constraint on `imagetocell_usage_log` so `log_image_conversion` is idempotent at the DB level — tracked separately.
- **Bolt-cap context cache no longer stale across sequential configs on the same worksheet.** `backfill_worksheet` now invalidates the 30-second usage cache in its `finally` block so a sibling config processed seconds later sees the consumption from the just-finished backfill. Closes the race where a second config could pass the budget gate using a snapshot taken before the first config consumed its share.

### Tests
- 72 new unit/integration tests under `backend/image-to-cell-3/tests/unit/test_bolt_*.py` covering each fix above plus the per-mode billing semantics (default, replace, name_map), preflight estimator paths, large-scale backfill workloads (200–1000 rows matching the customer-reported scale), retry-exhaustion paths, cache invalidation, and the `log_usage` / `state.save` ordering. Mock `mock_supabase` extended in `tests/unit/conftest.py` to honour `range(start, end)` and `in_("row_id", [...])` so chunking and pagination paths are end-to-end testable without a real Supabase. Full i2c-3 suite: 91/93 pass; the two remaining failures are pre-existing path-traversal tests in `test_temp_file_manager.py`, unrelated to this work.

## [1.1.0] - 2026-04-30

**Category:** Backend · **Impact:** MINOR

Shipped as part of platform release **1.2.0**.

### Added
- **Backfill hard-cap control.** The mid-job bolt-cap gate (`get_remaining_image_capacity`) now runs per row inside the backfill workers, truncating the per-row attachment batch to the remaining affordable image count when the org is approaching its plan ceiling. When `remaining <= 0` the row is skipped (not failed) so the cap is enforced without poisoning the backfill result. Reasons surface in logs as `Stopping - {Hard cap reached | Free plan limit reached | Insufficient bolts for one image}` for support visibility.

### Fixed
- **Large backfills no longer fail with `JSON could not be generated` (Supabase 400).** `StateRepository.get_batch()` previously sent every Smartsheet row ID for a sheet in a single PostgREST `in.(...)` filter. Sheets with ~400+ attachment-bearing rows produced a > 8 KB query string that Supabase Cloud's edge (Cloudflare) rejected with a generic 400, causing backfill to abort in ~5 s with `0 processed, 0 skipped, 0 failed` regardless of how many rows actually had attachments. The reader now pages through row IDs in chunks of 200 (`_GET_BATCH_CHUNK_SIZE`) and merges results — backfill on a 1652-row sheet now reads cleanly and processes every eligible row. Symptom previously confused for `BACKFILL_MAX_PAGES` exhaustion; this is the actual root cause.
