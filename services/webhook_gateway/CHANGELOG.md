### Changed
- **SH-227 / SH-228 / SH-229 / SH-231 — registry-backed gateway control plane.** Registrar, secret sync, and stream publisher share one `ToolRegistry`. Callback URLs and ownership prefixes use `spec.provider` (no hardcoded `/webhook/smartsheet/` in registrar). Unknown publish slugs return ingress `404 "unknown tool"` (fail closed — no orphan Redis streams). Dual name `i2c` / `smart-image-to-cell` resolves explicitly via `stream_name=i2c` on the I2C registry entry. Tests: `test_sh227_tool_registry.py` + existing suite.
- **SH-215 / SH-206 — provider-scoped secret cache keys.** The verification cache moved from `webhook-secrets:{org}:{tool}` to `webhook-secrets:{org}:{provider}:{tool}`, and the format now lives in `smarthub_core.webhooks.secret_cache` so tools writing the same cache cannot drift from the gateway. Without the provider segment a tool listening to two providers shared one `{webhook_id: secret}` map, and the "try every secret until one validates" loop could verify a callback against a secret issued by the other provider. `WebhookSecretSource` and `WebhookToolSpec` carry `provider` so tool config is explicit. The m2m route is now `PUT /internal/v1/webhook-secrets/{provider}/{tool_slug}/{org_id}` and only that: the path mirrors the cache key and the provider is never implicit. **No DB or schema change — Redis only, TTL-bounded. Cell History 2 untouched.** Tests: `test_sh215_provider_scoped_secrets.py`.
- **SH-215 — no compatibility read for the pre-SH-215 key.** A first cut dual-read `webhook-secrets:{org}:{tool}` and deleted it on write. It was dropped after checking what it actually protected: I2C verifies HMAC against Postgres (`imagetocell_webhooks` via its own repo) and never reads this cache, the only tool that wrote the old key was SmartQR (fixed in the same PR), and the gateway has not yet served a real callback for anyone. So the fallback covered a window that does not exist, while adding a permanent read of a key nothing may write plus a `DEL` on every write. Worst case without it is a 401 for up to one lifecycle interval (300s, same as the cache TTL) in an environment with no live callbacks, and it self-heals on the next sync from Postgres.
- **SH-208 / SH-206 — multi-tool secret sync (I2C + SmartQR).** Lifecycle pull-sync reads `imagetocell_webhooks` and `smartqr_webhooks` (AES-GCM via shared `APP_CRYPTO_KEY`) into `webhook-secrets:{org}:{tool}`. SmartQR can be disabled with `SMARTQR_SECRET_SYNC_ENABLED=false`. **Cell History 2 is not synced.** Tests: `test_sh208_multi_tool_secret_sync.py` + existing SH-173 cases.

### Added
- **SH-210 / SH-206 — gateway-owned webhook lifecycle (register / renew / zombie).** New `gateway/lifecycle/registrar.py` reconciles Smartsheet webhooks against each tool's active configs: registers missing, re-enables disabled, recreates definitive failures, waits out `NEW_NOT_VERIFIED` under `WEBHOOK_REGISTRAR_MIN_AGE_MINUTES` (10), rewrites callback-URL drift to `{base}/webhook/smartsheet/{tool}/{org}`, and deletes zombies with no active config. Webhooks owned by another org are protected and the cycle is fail-closed when the ownership lookup errors (no deletes, no destructive pre-cleanup). Secrets captured on register are encrypted into the tool table and merged into `webhook-secrets:{org}:{tool}`. Gated by `RUN_WEBHOOK_REGISTRAR` (default **false**) and `WEBHOOK_REGISTRAR_TOOLS` (default `smart-image-to-cell`); a tool must set `RUN_LIFECYCLE_POLLER=false` before being listed. **Cell History 2 has no spec here.** Tests: `test_sh210_webhook_registrar.py`.
- **SH-172 / SH-153 — Gateway scaffold + `stream:i2c` publish.** FastAPI service under `services/webhook-gateway/`: challenge handshake, HMAC verify via Redis secret cache, `StreamPublisher` XADD envelopes to `stream:i2c`, Dockerfile + `docker-compose.phase3.yml`. Unit tests for routes/registry.
- **SH-173 (MVP) — Lifecycle secret sync.** Under Redis lock `lock:lifecycle:manager`, decrypt `imagetocell_webhooks.shared_secret` and populate `webhook-secrets:{org}:smart-image-to-cell`. Register / renew / zombie cleanup remain on i2c until post-cutover.
- **Staging deploy templates.** `deploy/ecs-task-definition.staging.template.json`, `stg-webhook-gateway-env.example.json`, `STAGING_PROVISION.md` (ECR / secret / ALB checklist). AWS provision is ops follow-up after SH-147 gate.
